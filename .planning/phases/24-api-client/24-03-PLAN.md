**Document structure:**

```markdown
# Leasefy AI Platform — Backend API V4 Specification

## Overview
- Purpose: API contract between frontend and backend
- Base URL: /api/v1/ai
- Authentication: Bearer token (JWT)
- Content-Type: application/json (except SSE)

## Endpoints

### POST /api/v1/ai/message
- Purpose: Send user message, receive streaming AI response
- Request body: { message, conversationId?, attachments? }
- Response: SSE stream (text/event-stream)
- Event types: message_start, agent_dispatch, agent_status, content_delta, decision, message_complete, error
- Detailed event schemas with examples

### GET /api/v1/ai/conversations
- Purpose: List user conversations
- Query params: ?page=1&limit=20&search=text
- Response: { conversations: [...], total: number }

### GET /api/v1/ai/conversations/:id
- Purpose: Full conversation with messages
- Response: { id, title, messages: [...], createdAt, updatedAt }

### POST /api/v1/ai/conversations
- Purpose: Create new empty conversation
- Response: { id, title, createdAt }

### DELETE /api/v1/ai/conversations/:id
- Purpose: Delete conversation and all messages
- Response: 204 No Content

### GET /api/v1/ai/decisions
- Purpose: List all decisions across conversations
- Query params: ?status=pending|resolved&category=cobranza
- Response: { decisions: [...], pendingCount: number }

### POST /api/v1/ai/decisions/:id/select
- Purpose: User selects a decision option
- Request body: { optionId, additionalContext? }
- Response: { status: 'accepted'|'executing', actionsTriggered: [...] }

### GET /api/v1/ai/briefings
- Purpose: List briefings (daily/weekly)
- Query params: ?limit=10&type=daily
- Response: { briefings: [...] }

### GET /api/v1/ai/briefings/latest
- Purpose: Get the latest unread briefing
- Response: Single briefing object

### GET /api/v1/ai/preferences
- Purpose: Get user AI preferences
- Response: BetaPreferences object

### PUT /api/v1/ai/preferences
- Purpose: Update user preferences (partial)
- Request body: Partial<BetaPreferences>
- Response: Full updated BetaPreferences
```

Each endpoint section includes:
- HTTP method and path
- Request schema (TypeScript + JSON example)
- Response schema (TypeScript + JSON example)
- Error responses (400, 401, 404, 500)
- Example curl commands

**Acceptance criteria:**
- All 10 endpoints documented with request/response schemas

## SSE Streaming Protocol

### Connection
POST /api/v1/ai/message
Accept: text/event-stream
Content-Type: application/json

### Event Format
data: {"type": "event_type", ...payload}\n\n

### Event Sequence
1. message_start — Always first. Contains conversationId, messageId
2. agent_dispatch — If agents needed. Contains array of agents
3. agent_status (N times) — Per-agent completion. Contains agentId, status, durationMs
4. content_delta (many) — Streaming text. Contains delta string
5. decision — If applicable. Contains full PendingDecision object
6. message_complete — Always last. Contains optional usage stats

### Termination
data: [DONE]\n\n

### Error Event
data: {"type": "error", "code": "rate_limit", "message": "..."}\n\n

### Client Reconnection
- Client should implement exponential backoff
- Include Last-Event-ID header for resumption
```

Include a complete example SSE session showing all events in order with realistic data.

## Agent Execution Events

### Agent Types
| Agent | Description | Typical Duration |
|-------|-------------|-----------------|
| cobranza | Collection & payment tracking | 1-2s |
| pipeline | Candidate management | 1-2s |
| mantenimiento | Maintenance coordination | 1-2s |
| documentos | Document generation & verification | 1-3s |
| comunicacion | Multi-channel communication | 1-2s |
| reportes | Report generation & analytics | 2-3s |

### Status Lifecycle
dispatching → running → completed | failed

### agent_dispatch Event
{ type: "agent_dispatch", agents: [{ id, agentType, taskDescription }] }
- Sent once when orchestrator decides to invoke agents
- Multiple agents can be dispatched simultaneously

### agent_status Event
{ type: "agent_status", agentId, status, durationMs?, error? }
- Sent per-agent as they complete or fail
- durationMs included when status = "completed"
- error included when status = "failed"

### Frontend Expectations
- Frontend shows agent badges immediately on agent_dispatch
- Updates individual agent status as agent_status events arrive
- Begins content streaming only after all agents complete
- Failed agents show retry button; retry sends new message
```

**Acceptance criteria:**
- All 6 agent types documented
- Status lifecycle clearly specified
- Event schemas with field descriptions
- Frontend rendering expectations documented
